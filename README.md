# Principles for Effective Interactive Visualizations — Quarto / reveal.js

A port of `Posit Conf.pptx` to a Quarto reveal.js deck, styled to the
**vibe-widgets** aesthetic, with the screen recordings replaced by sixteen live
demo widgets — every one of them generated by `vw.create()` / `vw.edit()`.

The deck runs in three chapters, one per term of the DATA + VISUALS +
INTERACTION equation: **data transformation** (how an interaction changes the
query), **visuals** (what the visuals do with a selection), and
**interaction** (how the user enters that selection, and how much of it stays
on screen as an object).

## Render

```bash
quarto render slides.qmd     # → slides.html
quarto preview slides.qmd    # live reload while editing
```

Requires Quarto 1.4+. Built and verified against Quarto 1.10.18.
In Positron: open the folder, open `slides.qmd`, hit **Render**.

Widgets are embedded with `<iframe data-src=...>` so reveal.js only loads each
one when you reach its slide — nothing runs in the background during the talk.
Each widget is its own iframe and its own vibe widget: hovering in one never
touches another. `close.html` appears on two slides (3 and 5) as the same
file, embedded twice.

## How the widgets were made

```bash
pip install -e /path/to/vibe-widget         # the library, editable
export OPENROUTER_API_KEY=...
python build/make_data.py                   # dataset (+ legacy geojson, unused now)
python build/make_reviews.py                # synthetic external reviews
python build/make_basemap.py                # real basemap image (needs network once, then cached)
python build/make_widgets.py                # fifteen vw.create() calls (≈1–2 min each)
python build/make_augment_v2.py             # the seventh widget (reviews join)
python build/revise_widgets.py wait "…"     # optional: vw.edit() follow-ups
VIBE_REPO=/path/to/vibe-widget node build/export.cjs   # → widgets/*.html
quarto render slides.qmd
```

`make_widgets.py` is the source of truth for what each of the fifteen
shared-shape widgets was asked to do. Every prompt shares one preamble (assembled by
`build_preamble()`: the data columns, the basemap-image contract for map
widgets, a strict pointer-math rule, the exact pixel size, and strict copy
rules — no headings, no explanatory prose, no code or SQL readouts, no
placeholder text) followed by a short spec for that widget.
`orthogonal.html` and the three `sel_*` widgets opt out of the basemap section
(`NO_MAP` in `make_widgets.py`) since none of them is a map.

Slide 16's three widgets share a `SCATTER_BASE` block the same way slides
18–19 share `BRUSH_BASE`: all three draw the identical chart (reviews on a
linear x, weekend wait on y), so the only thing varying across the row is
what the selection does to it — remove the marks, recolour them, or add a new
one. `sel_highlight` is told in as many words that colour is the *only* thing
it may change: no rule, mean marker, difference readout or annotation of any
kind, because the slide's claim is that highlighting leaves the chart alone.

The six brush widgets on slides 18 and 19 additionally share a single
`BRUSH_BASE` block: the same task ("select a rectangular area, see how many
shops are inside"), the same marks and the same two-line readout. Only the
paragraph after it differs — the input method on slide 18, the reification
level on slide 19 — so that what the audience sees changing between the three
cells really is only the thing under discussion. (Slide 18's three widgets
land on the same 21 shops / 24.1 min for the same region, which is the point.) `augment.html` is generated by
its own script, `make_augment_v2.py`, because it needs a `reviews` input the
shared pipeline doesn't carry. Model: `google/gemini-3.1-pro-preview` through
OpenRouter, theme `vibe-widgets` (the library's built-in theme).

`export.cjs` does what the notebook would do at render time — inject React,
`tw`/`css`, and a model holding `data`, `basemap_image`, and `reviews` — and
bundles it all with esbuild into one file, fetching `d3` from esm.sh once at
build time. The deck therefore needs no network and no kernel. (`reviews` is
present in every widget's model for simplicity even though only `augment`
reads it — harmless, just a little bundle bloat for the others.)

### The 33rd shop is a deliberate outlier

`make_data.py` generates 32 shops from a fixed `RAW` table under a fixed seed,
then appends one more by hand: **Bayou City Original**, a tourist-flagship
downtown shop with 5,600 reviews against everyone else's 237–1,829. It exists
for slide 16's "remove elements" widget — with it in frame the review axis
runs to 6,000 and the other 32 shops pile into the left third; brush it away
and the axes re-fit and the rest spread across the full width, which is the
whole argument that removal is a *visual* consequence and not just a filter.

It is appended after the generated rows precisely so those 32 stay
byte-identical, and its wait time (44 min) only *ties* the existing maximum,
so the wait-encoded map widgets and the two answers hard-coded on slide 9
("Bagby Rings, 0.35 mi" and "28.3 min average weekend wait in the Heights")
are all unchanged. Re-running `make_data.py` then `make_reviews.py`
reproduces the whole dataset exactly.

### The basemap is a real map, not a schematic

`build/make_basemap.py` fetches OpenStreetMap tiles for the deck's bbox once,
stitches and crops them to the exact bbox, and recolors the result to a
two-tone bone/ink duotone that sits quietly behind the accent-colored marks
(small "© OpenStreetMap contributors" credit baked into the image's corner,
per OSM's tile usage policy). Every map widget receives this as a
`basemap_image` data-URL input and renders it as one SVG `<image>`,
positioned by projecting the image's two geographic corners with the exact
same d3 projection used for the shop marks — that's what keeps the image and
the marks pixel-aligned. Widgets are told not to draw their own roads, water,
loop, labels, or any bounding circle: the image already shows all of that.
(One consequence: a few of Houston's real toll roads and railways render with
a dashed cartographic style in the source tiles — that's genuine map content,
not a leftover schematic circle.)

### Pointer math inside a scaled, embedded iframe

Every map widget renders inside an `<iframe>` inside a reveal.js slide that
itself gets a CSS `transform: scale(...)` to fit the window — this breaks two
common shortcuts. `d3.drag`'s `event.x`/`event.y` and `d3.pointer(event,
node)` both rely on `SVGElement.getScreenCTM()`, which does not correctly
account for an ancestor iframe living inside a transformed page and silently
returns the wrong offset. Every widget instead computes pointer position by
hand: `event.sourceEvent.clientX/clientY` (real, transform-aware values the
browser delivers correctly) minus the target SVG's own
`getBoundingClientRect().left/top`. `structure.html`'s marquee-select is
hand-rolled with plain pointer events for the same reason, rather than
`d3.brush()`.

A second, unrelated pitfall bit `parameterize.html` specifically: its React
effect that built the SVG originally listed the dragged `target` state in its
own dependency array, so every drag tick tore the SVG down and rebuilt it —
including detaching and re-creating the very node the in-progress drag
gesture was bound to, which is what actually caused the reported "the target
jumps away from the cursor and stops tracking it" symptom. The fix splits
"build the SVG once" (deps: only the basemap image) from "update the existing
marks on every interaction" (deps: the interactive state) into two effects —
the same pattern `augment.html`, `close.html`, and `structure.html` already
used, which is why only `parameterize.html` needed it.

### The augmentation widget joins a real external source

The original `augment.html` computed distance and walk time from a draggable
marker — a client-side calculation, not really "an external source." The
current version clicks a shop and pulls in review text `donut_shops.csv`
never had, joined in from `data/houston_donut_reviews.csv` (a synthetic
reviews source, `build/make_reviews.py`) keyed by `shop_id` and passed to the
widget as its own `reviews` input. The panel visually sets the reviews
section apart from the shop's own fields to make the join legible.

## The aesthetic

Tokens come from the vibe-widget library's own built-in `vibe-widgets` theme
(`vibe_widget/themes.py`) and from vibewidget.dev:

| role | value |
|---|---|
| ground (bone) | `#F2F0E9` |
| lifted surface | `#FBFAF6` |
| ink | `#1A1A1A` |
| accent | `#F97316` (deep `#EA580C`) |
| display type | Space Grotesk |
| data type | JetBrains Mono |
| shadows | hard offsets, 2–8px, zero blur |
| borders | 2px slate, square corners |

Stage colors for the three loop stages keep the original deck's coding:
parameterization `#3F8BDB`, structuring `#478D4B`, augmentation `#E65100`.
The three hypotheses get their own colors, used for the dots inside the
hypothesis space on slide 2, the cards beside it, and the widget labels on
slide 5: wait times `#0F766E`, where is close `#6B3FA0`, pumpkin spice `#9F2D1F`.

## Notes on the port

- **Houston, not Seattle.** The recordings were Seattle; the title slide asks
  about Houston. The shops are fictional and sit in real neighbourhoods on a
  real basemap.
- **No footer, no reprise slide.** The deck opens straight from the title
  into the question; the old "posit::conf · principles for effective
  interactive visualizations" footer and the second title-reprise slide are
  both gone.
- **Slide 2's three hypotheses are reveal fragments**: each click reveals a
  dot in the hypothesis space and its matching card. No widget here — it's
  just the question.
- **Slide 3** is the ineffective example: the (non-overlapping)
  Hypotheses/Interactive-Vis diagram next to `orthogonal.html`, a genuinely
  interactive chart that answers none of the three hypotheses.
- **Slide 4** is the effective counterpart: the same diagram with the circles
  closer together, one hypothesis dot (purple, "where is close") drawn inside
  their overlap, and `close.html` embedded in place of the two old static
  screenshots — a live widget that *does* answer that hypothesis.
- **Slide 6 ("Overlap")** starts with two separate circles — Hypotheses, and
  Interactive Visualization — and slides them together into one merged
  circle on a single click (a CSS `transform` transition on an
  otherwise-visible fragment, not the default fade). The merged circle still
  reads only "Interactive Visualization"; the next click sets **Effective**
  in italics above it, which is the word the whole talk is arguing for."
- **Slide 7 ("Interactive visualizations can have 3 parts to answering a
  question")** reveals DATA, then +VISUALS, then +INTERACTION, then the final
  =Interactive Visualization circle, one fragment click at a time.
- **Slide 9 ("The loop")** pairs ASK with SEE for each of its three example
  questions: asking a question bolds ASK and shows the question (hiding
  whichever answer was showing before); the next click bolds SEE instead and
  reveals that question's answer, computed from the real dataset (e.g. the
  actual nearest shop, the actual average weekend wait in the Heights). The
  diagram column uses `align-items: start` (not `center`) so it stays put as
  the card column below it grows — centering it against a growing column was
  what made it visibly drift on every click.
- **The three chapter dividers** (slides 8, 14, 17) each show the whole
  DATA + VISUALS + INTERACTION equation with every term but that chapter's
  own grayscaled (`.eq-term.is-dim` → `filter: grayscale(1)`). The result
  circle is never dimmed — it is the goal, not one of the three stages.
- **A small three-dot "where are we" indicator** sits in the top-right corner
  from the chapter-1 divider onward (`.mini-stages` in the theme), a tiny
  horizontal echo of slide 7's DATA/VISUALS/INTERACTION circles rather than a
  parameterization/structuring/augmentation tracker: DATA alone lights up on
  the chapter divider, DATA and INTERACTION light up (VISUALS stays gray) for
  every slide from "The loop" through "Growing data."
- The three "in the wild" screenshot slides from the original pptx were
  removed.
- **Slide 15 ("Interaction customizes what the visuals say")** is the zoo of
  visual responses — selection, arrangement, elaboration, explore, encode —
  as five icon cards, each its own fragment so they arrive one at a time.
  Selection is highlighted as the one the talk actually opens up; the rest
  link out to the interaction zoo.
- **Slide 16 ("One selection, three things the visuals can do with it")**
  runs one select through three different consequences, named for what they
  do to the marks: **Remove Elements**, **Change Elements**, **Add Elements**.
  Each caption carries a shrunk copy of slide 2's hypothesis space with a
  different one of its three dots lit (`.hyp-mini`, the dot inheriting the
  cell's `--hyp`), so the row reads as one selection reaching three different
  questions rather than three unrelated demos.
- **Slides 18–19** are the instrumental-interaction pair. 18 varies the
  *input* for one identical selection; 19 varies how much of the selection
  survives the gesture, ending on reification.
- **Slide 20 ("Three parts, three decisions")** closes the loop opened on
  slide 7, giving each circle its two- or three-word summary.
- The SQL blocks on slides 10–12 are donut-flavored (matching each widget's
  actual interaction: distance-ranked shops for parameterization, a
  constructed `grp` column for structuring, a joined `walking_distances`
  source for augmentation) — the original pptx used sea-ice examples. The
  widgets themselves still show no query text — only the interaction and the
  numbers it produces.
- Slides 9–11 no longer carry a `[live] ...` caption line under the widget —
  the widgets speak for themselves. `parameterize.html`'s 2x2 stat-tile grid
  (shops in range / mean rating / weekend wait / price level) is gone for the
  same reason; that stat-tile visual pattern now lives in `augment.html`
  instead, as two small tiles (rating, price level) above its reviews list.
- The deck is 1280×720 and scales to any display.

## Interaction reference

| widget | what to do |
|---|---|
| orthogonal | hover a shop · click a `$`/`$$`/`$$$` chip to filter by price level |
| wait | hover a shop |
| close | drag the "you are here" marker · hover a shop |
| spice | flip the "pumpkin spice only" toggle to filter down to pumpkin-spice shops · hover a shop |
| parameterize | drag the target · move the radius slider · arrow keys nudge |
| structure | pick Group A / Group B / Clear, then click a shop or drag a brush · Undo · Reset |
| augment | click a shop to pull its reviews · hover any shop for its name |
| sel_filter | drag a region to remove those shops — the axes re-fit · reset brings them back |
| sel_highlight | click a neighborhood row to recolour its shops · nothing else on the chart moves |
| sel_count | drag a region · its card shows the count and inside-vs-outside means |
| in_drag | press, drag, release |
| in_corner | click one corner, then the opposite one |
| in_center | click anywhere to place a fixed-size region |
| re_none | drag a region — it disappears the moment you let go |
| re_move | drag a region, then drag the region itself to move it |
| re_handles | drag a region, then drag its corners to resize or its middle to move |
