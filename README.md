# Principles for Effective Interactive Visualizations — Quarto / reveal.js

A posit::conf talk, built as a Quarto reveal.js deck, styled to the
**vibe-widgets** aesthetic, with sixteen live demo widgets — every one of them
generated by `vw.create()` / `vw.edit()` — plus a wall of twenty recorded
interaction techniques on the opening and closing slides.

Twenty-seven slides in three chapters, one per term of the DATA + VISUALS +
INPUTS equation. Each chapter has the same shape: an animated divider, three
worked examples, and a **principle slide** that states the one thing to take
away.

| Chapter | The principle | Proof widgets |
|---|---|---|
| Data | Treat interactions like data queries — do they enable access to, and transformation of, the underlying data? | `parameterize` · `structure` · `augment` |
| Visuals | Strategically remove, edit and add elements to make comparisons easy to see | `sel_filter` · `sel_highlight` · `sel_count` |
| Inputs | Inputs should be as easy to adjust as they are to express | `in_drag`/`in_corner`/`in_center` · `re_none`/`re_move`/`re_handles` |

## Render

```bash
quarto render slides.qmd     # → slides.html
quarto preview slides.qmd    # live reload while editing
```

Requires Quarto 1.4+. Built and verified against Quarto 1.10.18.
In Positron: open the folder, open `slides.qmd`, hit **Render**.
Quarto ships inside Positron at
`/Applications/Positron.app/Contents/Resources/app/quarto/bin/quarto`.

## The 24px type floor

Nothing on a slide is smaller than **24px** — 0.8em at the 30px root, and 24
units in an SVG viewBox, which renders about 1:1 at this stage size. `$floor` in
the theme is that value; use it rather than writing a smaller number. To audit
after a render, paste this into the console on `slides.html`:

```js
Reveal.getSlides().flatMap((s, i) =>
  [...s.querySelectorAll('*')].filter(e => !e.closest('.exwall'))
    .filter(e => [...e.childNodes].some(n => n.nodeType === 3 && n.textContent.trim()))
    .map(e => ({ slide: i + 1, px: parseFloat(getComputedStyle(e).fontSize), text: e.textContent.trim().slice(0, 40) }))
    .filter(r => r.px < 24));
```

Two rules were quietly fighting this floor, and both are now overridden in the
theme:

- **reveal clamps iframes.** `.reveal section iframe { max-width: 95%;
  max-height: 95% }` shrank every widget by 5%, and capped the transform-scaled
  ones at 95% of the size their scale was counting on.
- **Quarto's code cascade compounds.** It sets `.reveal pre` to
  `$code-block-font-size` and `.reveal pre code` to `1em` *of that*, plus its own
  padding — so an `em` size on a `code` inside a `pre` is applied twice and the
  padding doubles. The SQL blocks state their size in pixels, once, at a
  specificity that outranks both.

**Inside** the widgets the floor is necessarily softer: the scatter and brush
widgets are 352px wide, where a 24px tick label would be a third of the axis.
The rule there is 15px minimum for any text, 28px or more for a number that is
the result of the interaction, at most four ticks per axis, and no label that is
not needed to read the result. Wherever a widget is alone on a slide it is shown
at 1.2×, which puts those 15px labels at 18px on screen.

## Showing a widget at a size other than its native one

```html
::: {.widget-wrap .sm-120}
<iframe data-src="widgets/sel_filter.html" title="..."></iframe>
:::
```

`sm-*` scales the 352×400 widgets, `wd-*` the 814×548 ones; the number is the
percentage. The iframe keeps its native pixel size, so the widget's own layout
is untouched, and is transform-scaled; the wrapper is sized to the scaled
result. Pointer math inside the widget works off its own
`getBoundingClientRect`, which the browser reports through the transform, so
hit-testing survives the scale — verified by drawing a region on the 0.46× and
1.2× embeds.

## Widgets must survive a slide change

The deck sets `preload-iframes: true` and `view-distance: 30`. With preload off,
reveal blanks every `iframe[data-src]` the moment you leave its slide: any state
you pre-staged is lost, and each per-cell fragment on a trio triggers a fresh
iframe load, which is a visible stall on stage. None of the widgets runs a timer
or an animation loop, so keeping all of them resident costs only startup — open
the deck a minute before you present.

## How the widgets were made

```bash
pip install -e /path/to/vibe-widget         # the library, editable
export OPENROUTER_API_KEY=...
python build/make_data.py                   # dataset
python build/make_reviews.py                # synthetic external reviews
python build/make_basemap.py                # real basemap image (needs network once, then cached)
python build/make_widgets.py                # fifteen vw.create() calls (≈1–2 min each)
python build/make_augment_v2.py             # the sixteenth (reviews join)
python build/make_wall.py                   # → _wall.qmd
VIBE_REPO=/path/to/vibe-widget node build/export.cjs   # → widgets/*.html
quarto render slides.qmd
```

`make_widgets.py` is the source of truth for what each widget was asked to do.
Every prompt shares one preamble (`build_preamble()`: the data columns, the
basemap-image contract for map widgets, a strict pointer-math rule, the exact
pixel size, and strict copy rules — no headings, no explanatory prose, no code
or SQL readouts, no placeholder text). `orthogonal` and the three `sel_*`
widgets opt out of the basemap section (`NO_MAP`) since none of them is a map.

Slide 17–19's three widgets share a `SCATTER_BASE` block and slides 23–24's six
share a `BRUSH_BASE` block, so the only thing varying across a row really is the
thing under discussion. (Slide 23's three land on the same count and the same
mean wait for the same region, which is the point.)

### Revising a widget

```bash
python build/revise_widgets.py sel_count "<what to change>"
bash build/revise_queue.sh mybatch sel_count re_move        # several at once
VIBE_REPO=... node build/export.cjs sel_count re_move
```

`revise_queue.sh` reads each request from `build/requests/<name>.txt` and gives
every run its own working directory — parallel runs in one directory collide on
the library's bundle filename, which is the current second plus a hash of the
cwd. Logs land in `build/logs/`.

`revise_widgets.py` hands a widget back exactly the inputs it was generated
with: `basemap_image` for the map widgets, and `reviews` as well for `augment`,
which would otherwise lose its join.

Model: `google/gemini-3.1-pro-preview` through OpenRouter, theme `vibe-widgets`.
Anthropic models fail there with HTTP 400 because the agent's tool names contain
dots.

## The example wall

Seven of the twenty slots show vibe-widget's own demos -- a table lens over
4,000 trial sites, a genome browser, sea ice against CO2, generations from a
model, robotic grasp candidates, a pendulum phase portrait and a spike raster.
`build/make_demo_clips.py` encodes those from the recordings in
`~/Downloads/vw_demo`. Each is dropped into a slot of nearly the same aspect
ratio, because the layout fixes a card's *width* and lets its height follow the
clip: a taller clip overlaps its neighbours. The two recordings that are taller
than they are wide are cropped to the part that carries the interaction.

`build/make_wall.py` lifts the wall block out of the Meros talk deck
(`~/Downloads/mx-examples/meros-deck/merosdeck.html`), whose `layout.py`
authored those card positions against the same 1280×720 stage this deck uses, so
the geometry transfers unchanged. It drops the `.webm` sources and the bare
`autoplay` attribute, keeping reveal's `data-autoplay`: the wall appears on two
slides, so 40 `<video>` elements exist in the document and letting the browser
start all of them at load would run 40 decoders for two slides' worth of
picture. reveal plays them when their slide becomes current and pauses them on
the way out.

Blur and veil are pure CSS, driven off the fragment with `:has()` — no script.
The closing slide carries `.is-focused` so it opens already blurred.

## Notes on the data

### The 33rd shop is a deliberate outlier

`make_data.py` generates 32 shops from a fixed table under a fixed seed, then
appends one more by hand: **Bayou City Original**, a tourist-flagship downtown
shop with 20,000 reviews against everyone else's 237–1,829. It exists for slide
17: with it in frame the review axis runs to 20,000 and the other 32 shops pile
into the leftmost tenth of the plot; brush it away and the axes re-fit and the
rest spread across the full width, which is the whole argument that removal is a
*visual* consequence and not just a filter.

**Changing the dataset takes two steps.** `make_data.py` writes the CSV, but every
widget bundle embeds its own copy at `build/out/data.json`, which `make_widgets.py`
writes. Refresh that file and re-export, or the widgets keep showing the previous
numbers -- the command is in a comment at the foot of `make_data.py`.

Slides 18 and 19 exclude it, because there the chart is the constant and the
selection is the variable — an outlier squashing the marks into one corner just
makes both harder to read.

It is appended after the generated rows precisely so those 32 stay
byte-identical, and its wait time (44 min) only *ties* the existing maximum, so
the wait-encoded map widgets and the answers on slide 11 (Bagby Rings at 0.35
mi, 28.3 min average weekend wait in the Heights) are all unchanged.

### What slide 18's dropdown groups by

Neighbourhoods do not actually cluster in reviews × wait — they hold one to four
shops each and separate no better than chance. Price level does: the three `$$$`
shops sit at 36–44 minute waits against means of 19 and 25 for `$` and `$$`. The
dropdown therefore offers the three price tiers first and the five largest
neighbourhoods after, so the demo's claim ("the selected group reads as a
cluster") is true of the data rather than asserted over it.

### The basemap is a real map, not a schematic

`build/make_basemap.py` fetches OpenStreetMap tiles for the deck's bbox once,
stitches and crops them to the exact bbox, and recolors the result to a two-tone
bone/ink duotone (with the "© OpenStreetMap contributors" credit baked into the
corner, per OSM's tile usage policy). Every map widget receives this as a
`basemap_image` data-URL input and renders it as one SVG `<image>`, positioned
by projecting the image's two geographic corners with the exact same d3
projection used for the shop marks — that is what keeps the image and the marks
pixel-aligned. Widgets are told not to draw their own roads, water, loop, labels
or bounding circle: the image already shows all of that.

### Pointer math inside a scaled, embedded iframe

Every widget renders inside an `<iframe>` inside a reveal.js slide that itself
gets a CSS `transform: scale(...)` to fit the window — and, for the scaled
embeds, inside a second transform of its own. This breaks two common shortcuts:
`d3.drag`'s `event.x`/`event.y` and `d3.pointer(event, node)` both rely on
`SVGElement.getScreenCTM()`, which does not account for an ancestor iframe
living inside a transformed page and silently returns the wrong offset. Every
widget instead computes pointer position by hand:
`event.sourceEvent.clientX/clientY` minus the target SVG's own
`getBoundingClientRect().left/top`. Rectangular brushes are hand-rolled with
plain pointer events rather than `d3.brush()`, which has the identical problem
internally.

### A d3 trap the model keeps hitting

`fitExtent` on a bbox **Polygon** collapses the map: the ring's winding makes
d3-geo fit the whole sphere and every mark lands on one point. The preamble asks
for `{type: "MultiPoint", coordinates: [corners]}` instead, and
`revise_widgets.py --fix-projection` repairs a widget that regressed.
